# AR-распознавание платы — дизайн

Обновлено: 2026-10-08 · Связанные документы: [формат данных и правила плана](../shared_boards/README.md), [план для iOS](ios-plan.md)

## Цель

Пользователь наводит камеру на материнскую плату, приложение распознаёт её и показывает поверх реальной платы разъёмы из сценария сборки. Тап по разъёму открывает инструкцию, прогресс чек-листа отражается на подсветке. Работает в трёх клиентах — iOS, Android и web — на общих данных из `shared_boards/`.

Первая плата: **Gigabyte B450 AORUS M (rev. 1.x)**, физический экземпляр есть у команды.

## Решения

| Вопрос | Решение |
|---|---|
| Способ привязки к плате | Image tracking по эталонному фото (ARKit / ARCore Augmented Images / MindAR) |
| Что показываем | Все разъёмы из шагов плана сборки (по ответам опроса), кроме заблокированных шагов; разъёмы текущего шага подсвечены ярче, выполненные приглушены |
| Место в приложении | Вкладка «Камера» открывается в AR; фото-режим остаётся запасным |
| Заморозка кадра | Есть во всех клиентах; основа — обобщённый фото-режим |
| Снимок | Хранит гомографию «мм платы → снимок»; метки на нём пересчитываются из текущего плана |
| Фото без AR | Плата ищется на снимке автоматически; не нашлась — пользователь ставит 4 угла платы |
| Порядок шагов | `requires` в данных: шаг заблокирован, пока не выполнены нужные |
| Единицы координат | Миллиметры |
| Отвергнуто | Ручная калибровка по углам вместо распознавания (осталась запасным путём на фото), ML-распознавание через Vision/Create ML (нужен датасет — избыточно для MVP) |

## 1. Контракт данных (`shared_boards`)

Полный формат (schemaVersion 3: опрос, этапы, кабели, варианты шагов, `requires`) — [`shared_boards/README.md`](../shared_boards/README.md); здесь — геометрия разъёмов.

```json
{
  "physical": { "widthMm": 244, "heightMm": 244 },
  "target": { "image": "target.jpg" },
  "connectors": [
    { "id": "atx", "name": "ATX",
      "rectMm": { "x": 210, "y": 78, "w": 12, "h": 58 } }
  ]
}
```

Значения `rectMm` в примере условные — реальные снимаются линейкой с платы.

- **`target.jpg`** — фото платы строго сверху, без бликов, обрезанное точно по краю платы, в ориентации схемы из руководства (задняя I/O-панель слева).
- **`rectMm`** — прямоугольник разъёма в мм; начало координат — левый верхний угол платы; `x`, `y` — левый верхний угол разъёма.
- **`physical`** — реальный размер платы; задаёт масштаб для AR-движка.

### Перевод в координаты якоря

Смещение центра разъёма от центра платы:

```
dx = x + w/2 − W/2
dz = y + h/2 − H/2
```

| Клиент | Система координат якоря | Позиция |
|---|---|---|
| iOS — `ARImageAnchor` | центр фото, плоскость XZ, метры | `(dx/1000, 0, dz/1000)` |
| Android — `AugmentedImage` | центр фото, плоскость XZ, метры | `(dx/1000, 0, dz/1000)` |
| Web — MindAR anchor | центр, плоскость XY, ширина цели = 1 | `(dx/W, −dz/W, 0)` |

Углы прямоугольника считаются той же формулой для `(x, y)`, `(x+w, y)`, `(x+w, y+h)`, `(x, y+h)`.

## 2. Опрос и план сборки

Перед чек-листом пользователь отвечает на опрос «Ваша сборка» (`setup` в `board.json`): число модулей памяти (1/2/4), NVMe, SATA SSD и HDD (по 0–3), видеокарта, корпусные вентиляторы, тип блока питания. Из ответов строится **план** — 14–22 шага в четырёх этапах (на столе → корпус → подключение → проверка), от установки процессора до первого запуска в BIOS. Правила построения одинаковы во всех клиентах и описаны в [`shared_boards/README.md`](../shared_boards/README.md#план-сборки).

- **Память:** подсвечиваются именно нужные слоты — 1 модуль → DDR4_1, 2 → DDR4_2 + DDR4_1 (двухканальный режим, руководство стр. 10), 4 → все.
- **Накопители:** по шагу на каждый диск; порты SATA раздаются по порядку (сначала SSD, затем HDD).
- **Кабели БП:** у силовых шагов есть блок «Со стороны блока питания» — где искать кабель у немодульного, полумодульного и модульного БП, и предупреждения (EPS 8-pin ≠ PCIe 6+2, кабели модульных БП разных моделей несовместимы).
- **Шаги без разметки** (БП, плата в корпус, первый запуск) есть только в чек-листе; когда такой шаг текущий, камера показывает плашку «Сейчас: …».
- **Порядок шагов** (`requires`): кулер — после процессора, вентилятор кулера — после кулера, плата в корпус — после заглушки I/O, видеокарта и монитор к плате — после установки платы, первый запуск — после всего, что нужно для POST. В плане `requires` раскрывается в конкретные шаги: повторы — в их экземпляры, шаги вне плана выпадают.

**Состояния шага:** `done` — отмечен; `current` — первый неотмеченный шаг плана; `locked` — неотмеченный, у которого выполнено не всё из `requires`; `pending` — остальные. Приоритет: `done` > `current` > `locked` > `pending`.

- У заблокированного шага галочка неактивна, вместо разъёма — «Сначала: …» (не больше двух названий, дальше «и ещё N»); его разъёмы не подсвечиваются.
- Снятие отметки снимает и отмеченные зависимые шаги, в том числе через другие, — после подтверждения со списком, одной операцией.
- Старое сохранение, где зависимый шаг отмечен раньше нужного, показывается как есть.

## 3. Архитектура клиентов и метки

Каждый клиент состоит из четырёх частей:

| Часть | Ответственность | iOS | Android | Web |
|---|---|---|---|---|
| **Tracker** | Найти плату, выдать якорь и состояние | ARKit + RealityKit; `ARReferenceImage` строится в рантайме из `target.jpg` | ARCore; `AugmentedImageDatabase.addImage` в рантайме | MindAR; `targets.mind` компилируется в CI |
| **BoardLayout** | `rectMm` → локальные координаты якоря | чистая функция | чистая функция | чистая функция |
| **Highlight** | Полупрозрачный прямоугольник, лежащий на разъёме (3D) | `ModelEntity` с plane mesh | нода с plane | mesh three.js |
| **Labels** | Метки-кнопки поверх камеры (2D), позиция = проекция центра разъёма каждый кадр | SwiftUI + `ARView.project` | Compose + проекция | HTML + `Vector3.project` |

Метки двумерные: всегда читаемы, удобно тапать, поддерживают крупный шрифт и выглядят так же, как в фото-режиме.

**Состояние метки** берётся из плана сборки (раздел 2): `current` — разъёмы текущего шага, `done` — выполненных, `pending` — остальных. Разъёмы, которых нет в плане, и разъёмы заблокированных шагов не показываются. Шаг может подсвечивать несколько разъёмов (два слота памяти); у текущего шага к имени разъёма добавляется подсказка («DDR4_2 · 2-й от CPU»).

### Метки без наложений

Метки строятся в четыре прохода, одинаково для AR и снимка:

1. Разъёмы, нужные только заблокированным шагам, отбрасываются.
2. Разъёмы с одинаковым `rectMm` склеиваются в одну подсветку и одну метку «SATA3 0 / SATA3 1». Состояние, шаг по тапу и подсказка берутся у главного разъёма: current > pending > done, затем порядок плана.
3. Подпись выполненного разъёма скрывается, если его прямоугольник пересекается с невыполненным (сокет под креплением кулера). Бледная подсветка остаётся.
4. Раскладка на экране: подписи ставятся по приоритету (current, pending, done; затем порядок плана и id). При наложении подпись сдвигается вверх или вниз на свою высоту, влево или вправо на свою ширину, и к разъёму рисуется выноска. Свободно ли место, проверяется уже после прижатия подписи к краю экрана. Места нет — подпись скрывается; текущая не скрывается никогда.

В AR раскладка с гистерезисом: смена места и появление подписи ждут 3 кадра подряд. Исключения — текущая подпись и момент, когда плата только что найдена: тогда всё ставится сразу. Снимок статичен, для него один детерминированный проход без истории.

## 4. Поток данных (заморозка, фото, фонарик)

1. **Загрузка.** iOS — `shared_boards` в бандле; Android — `shared_boards` как дополнительная папка assets в Gradle; web — JSON и `targets.mind` в сборке.
2. **Открытие «Камеры».** Проверка поддержки AR (`ARWorldTrackingConfiguration.isSupported` / `ArCoreApk.checkAvailability` / камера + WebGL) → эталон из `target.jpg` и `physical.widthMm` → запуск сессии.
3. **Состояния трекинга** (одинаковые во всех клиентах):

   | Состояние | Когда | Подсказка |
   |---|---|---|
   | `searching` | плата не найдена | «Наведите камеру так, чтобы плата целиком попала в кадр» |
   | `tracking` | якорь есть | — (показаны метки) |
   | `limited` | трекинг потерян | «Плата потеряна — наведите камеру снова»; метки скрыты |

4. **Плата найдена** — один раз создаются подсветки и метки; дальше каждый кадр обновляются только экранные позиции меток. Метки за пределами экрана или за камерой скрываются.
5. **Тап по метке** — существующий экран инструкции для шага.
6. **Шаг отмечен** (в инструкции или чек-листе) — сессия обновляется, AR-вью перекрашивает подсветки без перезапуска трекинга.
7. **Уход с вкладки** — пауза сессии; возврат — продолжение, при потере якоря — `searching`.

### Заморозка кадра

В состоянии `tracking` доступна кнопка «Заморозить»:

1. Снимается кадр камеры без 3D-подсветки (iOS — `ARView.snapshot` со скрытой подсветкой; Android — `PixelCopy`; web — `<video>` на canvas с той же обрезкой, что на экране).
2. Четыре угла платы проецируются на экран в координатах того же обрезанного кадра; по ним считается **гомография** «мм платы → снимок».
3. Снимок и гомография передаются в **`BoardPhotoView`** — обобщённый фото-режим. Метки (центр + полигон в перспективе) считаются через гомографию из текущего плана при каждой отрисовке: включили вентиляторы в опросе — SYS_FAN появляются на уже замороженном кадре. Зум, тапы, переход к инструкции и подсветка текущего шага реализованы один раз.

«Вернуться в AR» возвращает живую камеру. Снимок хранится только в памяти сеанса. Если плата не находится (например, видеокарта уже закрывает её), пользователь замораживает кадр заранее или переходит в фото-режим.

### Фото

Снимок с камеры телефона или из галереи тоже превращается в «снимок + гомография»:

1. Поворот по EXIF применяется до всего остального, иначе на портретных фото с iPhone метки легли бы на повёрнутую картинку.
2. **Распознавание** (web). Для снимка, уменьшенного до 1280 px, создаётся отдельный `Controller` MindAR под его размер, с тем же `targets.mind`. Детектор MindAR видит квадратное окно примерно в половину меньшей стороны, поэтому проходятся 9 окон. Пары точек «эталон → снимок» берутся у матчера (`inlierMatches2` в `debugMode`), эталон переводится в мм через `physical`. Гомография — DLT с нормализацией Хартли и RANSAC (порог 4 px), параметры камеры не нужны. После распознавания контроллер и его тензоры TF.js освобождаются вручную: `dispose()` в MindAR 1.2.5 этого не делает.
3. **Проверка результата:** четырёхугольник углов платы без самопересечений, выпуклый, с обходом по часовой, занимает ≥ 3 % снимка, пропорции близки к `physical`. Углы за краем снимка допустимы.
4. **Не нашли** — пользователь ставит 4 угла платы по подсказке с мини-схемой («Коснитесь угла платы 1 из 4: у задней панели, со стороны процессора»), затем может их перетаскивать; метки обновляются на лету. После четвёртого угла проверяется форма: «бантик» почти всегда означает перепутанные соседние углы → «Похоже, углы перепутаны — проверьте порядок», метки не показываются. Тот же режим служит для правки автораспознавания («Поправить углы»).

Автораспознавание фото есть в web; в iOS и Android фото пока размечается по 4 углам, распознавание появится вместе с AR.

### Фонарик

Кнопка в AR, если камера поддерживает фонарик (web — `getCapabilities().torch` у видеотрека: есть в Chrome на Android, в iOS Safari нет — кнопка скрыта). При заморозке и уходе с вкладки фонарик гаснет, при возврате в AR включается снова.

## 5. Обработка ошибок

Принцип: любая ошибка ведёт в фото-режим, тупиков нет.

| Ситуация | Поведение |
|---|---|
| Нет доступа к камере | Объяснение + «Открыть настройки» (web — текстовая инструкция) + «Выбрать фото из галереи» |
| AR не поддерживается | Сразу фото-режим с пометкой. Android — сначала предложить установить ARCore (`ArCoreApk.requestInstall`). Web во встроенном браузере — совет открыть в Safari / Chrome |
| Битые данные платы | AR для платы недоступен → фото-режим, без падения; запись в лог. Основная защита — CI |
| Эталон отклонён движком | iOS `ARReferenceImage.validate`, Android `ImageInsufficientQualityException`, web — ошибка загрузки `.mind` с «Повторить» → как битые данные |
| Долгий поиск | ~10 с — советы (свет, расстояние, плата целиком, «Поддерживается Gigabyte B450 AORUS M»); ~25 с — крупная кнопка «Перейти в режим фото» |
| Трекинг потерян | Метки скрыты, «Заморозить» неактивна, подсказка |
| Прерывание (звонок, сворачивание) | Пауза и продолжение; iOS `sessionWasInterrupted`, Android `onPause`/`onResume`, web `visibilitychange` |
| Ошибка заморозки | Тост «Не удалось сохранить кадр», остаёмся в AR |
| Web: долгая загрузка | Экран загрузки с прогрессом (TF.js, `.mind`) |
| Плата на фото не найдена | Тост «Плату на фото не нашли — отметьте 4 угла», разметка по углам |
| Углы перепутаны | «Похоже, углы перепутаны — проверьте порядок»; метки не показываются, пока форма не исправлена |
| AR дозапустился, когда пользователь уже ушёл в фото | AR остаётся на паузе, фото не перебивается |
| Камера без фонарика | Кнопки нет |

## 6. Тестирование и критерии готовности

1. **Данные — `shared-boards.yml`.** `validate.mjs` для схемы v3: ссылки между опросом, этапами, разъёмами, пулами, кабелями и шагами; `requires` ссылается на существующий шаг выше по списку и не на сам шаг; `target.jpg` существует и его пропорции совпадают с `physical` (±3 %); `rectMm` внутри платы; у подсвечиваемых разъёмов есть `rectMm`; разъёмов в пулах хватает на максимальные ответы; общие фикстуры `layout-cases.json` и `plan-cases.json`.
2. **Общая математика.** `shared_boards/fixtures/layout-cases.json` — входы и ожидаемые выходы (смещение в метрах, 4 угла, web-координаты). Прогоняется в каждом клиенте: XCTest (`ios.yml`), JUnit (новый `android.yml`, Gradle `test` на ubuntu), Vitest (`web.yml`, до деплоя).
3. **План и логика меток** (юнит-тесты на каждой платформе): общие фикстуры плана `plan-cases.json`, включая раскрытие `requires` (повторы, повтор в 0 экземпляров, шаг вне плана); приоритет `done` > `current` > `locked` > `pending` и старое сохранение; подпись «Сначала: …» с обрезкой; список зависимых при снятии отметки («ромб» CPU → кулер → первый запуск); снятие одной операцией; скрытие разъёмов вне плана и locked; склейка; скрытие выполненных; раскладка подписей (две текущие видны обе, детерминированный порядок, край экрана, гистерезис); point-in-polygon для меток на снимке; сдвиг текущего шага после отметки.
4. **Гомография:** точное решение по 4 точкам; нормализация Хартли (мм → 4000 px без потери точности); вырожденный вход → нет решения; RANSAC с 30 % выбросов на детерминированном генераторе; проверка четырёхугольника («бантик», обход против часовой, углы за кадром).
5. **Web e2e** (Playwright, отдельный job в `web.yml`; деплой — после юнит- и e2e-тестов). WebGL на SwiftShader, three и MindAR — из `node_modules` вместо CDN. Сцены генерируются из `target.jpg` с известной гомографией: 4 ракурса и мелкая плата (~12 % кадра), точность углов ≤ 1 % диагонали; JPEG с EXIF Orientation = 6; чужая картинка → разметка по 4 углам; 5 фото подряд — число тензоров TF.js не растёт; заморозка с фейковой камерой (`.y4m`) → включённые вентиляторы появляются на кадре; кнопки фонарика нет; галочка locked-шага неактивна; снятие CPU — подтверждение со списком.
6. **Качество эталона** (вручную при замене `target.jpg`): `arcoreimg eval-img` ≥ 75 через `shared_boards/scripts/check-target.sh`; отсутствие предупреждений Xcode; успешная компиляция `.mind` в `web.yml`.
7. **Ручная проверка на плате:** распознавание с 30–60 см, под углом до ~45°, при лампе и дневном свете; приближение вплотную к ATX после распознавания; установка видеокарты после распознавания; заморозка → зум → тап → инструкция → отметка шага; фото с телефона — автораспознавание, 4 угла, «Поправить углы»; фонарик — кнопка есть в Chrome на Android, нет на iPhone; запрет камеры, прерывание, долгий поиск; web в Safari (iOS), Chrome (Android), встроенном браузере Telegram.

### Критерии готовности MVP

- Плата распознаётся за ≤ 3 с при нормальном освещении.
- Подсветка совпадает с разъёмом с точностью ~5 мм на расстоянии 40 см.
- Тап открывает инструкцию; отметка шага перемещает подсветку.
- Заморозка кадра работает в iOS, Android и web; снимок отражает текущий опрос и прогресс.
- Подписи меток не перекрывают друг друга.

## Вне рамок

3D-модели кабелей, несколько эталонов на плату, ручная калибровка по углам в AR, ML-распознавание, автоопределение «другой платы», телеметрия, сохранение и шаринг замороженных кадров и фото.
